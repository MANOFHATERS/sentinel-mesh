Project summary

Sentinel Mesh

A security team that never sleeps, built as software: it watches for attacks, checks the software a company depends on, and fixes problems, while a human approves every serious action.

The problem

Small and mid-size companies cannot keep up with attacks

  • Too many alerts.Security tools raise thousands of alarms a day. Most are false. A tired person has to read them all.
  • Not enough people.Companies of this size cannot afford a 24-hour security team, so real attacks get missed or found late.
  • Attacks come through other people's software.A company uses hundreds of packages written by others. One weak package can put every product that uses it at risk. This is called a supply-chain risk.
  • Writing the fix is slow.Even after a flaw is found, someone must find the bad code, write a patch and open a pull request.
  • Automation is scary.A tool that acts alone can lock out a real employee or break a system. Companies need speed and a human in control.

Goal: cut the noise, find the real attacks, respond fast, and keep every action approved by a person and recorded.

The solution I built

Five cooperating agents, one approval gate, one record

  • 1. Triage.Reads the raw alert feed and scores each alert. A trained detector keeps the likely attacks and drops most of the noise, so people see far fewer alerts.
  • 2. Investigation.Takes an alert and gathers evidence: what happened before it, which techniques from the MITRE ATT&CK catalogue match, and a plain-language explanation.
  • 3. Containment.Chooses a response, such as blocking an IP address, isolating a machine or disabling an account. It never acts on its own for risky steps.
  • 4. Supply-chain agent.Builds a map of packages and who depends on whom. A graph neural network ranks which packages are the riskiest, including risk inherited from what they depend on.
  • 5. Code-fix agent.Scans a repository, finds weak code, and drafts a pull request with a fix. It never merges the change itself.
  • Human Approval Gate.Every action that changes something waits for a person to approve it.
  • Tamper-evident audit log.Every step is written to a chain of records. If anyone edits history, the chain breaks and it shows.
  • Real login and roles.Sign-in needs a username, a password and a one-time code from an authenticator app. There is no sign-up page. Each role (analyst, auditor, viewer) sees only the controls it is allowed to use.
  • A dashboard.One website with the overview, incidents, a live alert feed, launchable scenarios, evaluation, models, audit, supply-chain map and code scan.

  • Synthetic demo.Generated traffic and a seeded example repository. It is repeatable and needs no downloads, so it is good for showing how the system works.
  • Real data.Sign in with a real-data account and the whole dashboard is rebuilt from public data. A badge in the header says which mode you are in.

What this project does not claim

  • The response policy learns from a simulator we wrote. No public dataset of real analyst decisions exists. Only the action names and the vulnerability ranking come from real sources.
  • The scanner is weak on flaws deep inside libraries. On simple application code it does better.
  • Connectors to Wazuh, GitHub, identity and Slack run against local look-alike servers, not live company systems.
  • The identity provider is a demo stand-in for Okta or Azure AD.
  • No real malicious-package scenario is built yet.
Accounts and roles

Why there is no "Create account" button

A security tool must not let strangers make their own account. Access is given by the company, never asked for.

  • No sign-up page, on purpose.If anyone could register, anyone could read incidents or approve actions. In a security product that is the biggest hole you can leave.
  • Accounts are made by the company's administrator.In real life that is the company's identity system (Okta, Azure AD). The administrator adds a person there, and that person can then sign in here.
  • The product never stores or handles a real password.The identity system checks the person and tells the dashboard who they are. That is called single sign-on (SSO).
  • In this demo, a small script makes the accounts.When the server first starts, it creates the demo accounts and writes their passwords to a local file. It plays the part of Okta.
  • A person who is in no approved group is refused.Access is opt-in. Being able to sign in to the identity system is not enough.
  • Removing someone is one step.Deactivate them at the identity system and their open sessions here are cancelled straight away.
Who decides what

How roles are made, and who is in charge

  • There are two roles.Analyst can see everything and can act: approve or reject, launch scenarios, replay the feed. Viewer can see everything but cannot act. Auditors get this one.
  • Roles come from groups, not from this app.The identity system puts each person in a group. The dashboard turns the group into a role: the group SOC-Analyst becomes analyst, and the group Auditor becomes viewer.
  • Who is "the main person"?The company's administrator at the identity system. They create accounts, put people in groups, and remove them. There is no all-powerful admin inside the dashboard itself.
  • In this demo.Maya is in SOC-Analyst, so she is an analyst. Omar is in Auditor, so he is a viewer. Carl is a contractor with limited access. Nina has no authenticator set up, so she is refused.
  • Machines use API keys.Scripts and break-glass access use long secret tokens. People do not sign in that way.
  • A role change applies at the next sign-in.The role is read when you sign in, not while you are already inside.
Why it is built this way, in one line each (your defence):
  • Least privilege. Each person gets only what their job needs.
  • Separation of duties. The person who checks (auditor) cannot be the person who acts, so checking stays honest.
  • One place to control access. Joiners, movers and leavers are handled once, in the identity system, not in every tool.
  • Second factor. A stolen password alone is not enough, because the code comes from a device.
  • Everything is recorded. Every sign-in, refusal and change goes into the tamper-evident log.
  • It is the market standard. Real companies work this way, so the demo shows the real shape.
Signing in with a code

The six-digit authenticator code

  • Setup, once.The server makes a random secret for the account and stores it. The same secret goes into the authenticator app (or the demo command).
  • At sign-in.You type your username and password.
  • Then the code.The app mixes the secret with the current time (in 30-second slices) and keeps 6 digits. That is the code.
  • The server checks.It does the same sum with its own copy of the secret and clock. If the numbers match, you are in.
  • Safe by design.Codes change every 30 seconds, work only once, and five wrong tries lock the account for five minutes.
  • In the demo.Run python scripts/dev_idp_accounts.py code maya.analyst@acme.example in the project folder and type the number at once.
The Overview page

What Maya sees after signing in

Three parts: eight status cards, three scenarios to launch, and a feed of alerts. Plus one button in the header.

The eight cards (a quick health check)

  • 1. Waiting for approval.How many proposed actions are stopped at the approval gate, waiting for a human to say yes or no. Nothing risky happens until this number is dealt with.
  • 2. Incidents.How many cases the system has opened so far, and how many raw alerts it took in to make them.
  • 3. Alert reduction.The share of alerts a person never had to read, because the system dismissed them as noise. Underneath: how many did reach a human. This is the main promise of the product.
  • 4. MTTD (mean time to detect).The average time from an alert arriving to the system deciding what it is. The target is under 30 seconds.
  • 5. MTTC (mean time to contain).The average time from that decision to an approved response, such as blocking or isolating. The target is under 3 minutes.
  • 6. Audit chain.Checks the tamper-evident log. "Verified" means no record was changed. "Broken" would mean someone edited history. It also shows how many records it checked and how long that took.
  • 7. Ungated executions.How many actions ran without approval. This must stay at 0. It is read back from the log, so it proves the gate cannot be skipped.
  • 8. Failed actions.Actions that were approved but did not work. Underneath: how many times the guardrails refused something outright.

The three scenarios you can launch

Each is a ready-made attack story. Pressing Launch scenario feeds its events into the system so you can watch it work and approve the steps.

  • Phishing to lateral movement.An employee clicks a phishing link. The attacker then spreads from that laptop to the file server using stolen admin logins. You watch the system detect each step and propose isolating the laptop and blocking the address.
  • Vendor-dependency CVE.Four security flaws are announced in an abandoned package hidden four levels deep in other companies' software. You see the map of who is exposed and approve a fix, which opens a tracking issue.
  • Malicious open-source package.An abandoned package changes owner and its new version steals secrets from build servers. It even hides a note telling AI scanners to ignore it. The system treats that note as plain text and still escalates. You approve isolating the build server.

In the real-data workspace this section is called "Launch a real case", and the cases come from real flows, real advisories and a real code scan.

The background feed

  • What it is.A stock of network events the system has not seen yet, held back on purpose.
  • What Replay does.You choose how many, and it pushes that many through the same pipeline. Most are dismissed as harmless. The ones that look like attacks join the approval queue.
  • Why it matters.The alert-reduction number on the cards is measured on exactly these events, so it is not made up.
  • The counter.It shows how many events remain. Only analysts see the Replay controls.

The live demo button

  • Where.The "Start live feed" button in the top bar.
  • What it does.It runs the feed for you automatically, a small batch every few seconds, so the numbers move on their own like a real security centre.
  • What you see.A running count on the button: how many came in, how many were dismissed, and how many need approval. The cards and the approval queue update as it goes.
  • Control.Click it again to stop, and again to resume. It ends when every held-back event has been used. Analysts only.

Phishing to lateral movement: what I say, screen by screen

A. I click Launch and three incidents appear

The card shows three lines, each “awaiting approval”. An incident is one case the system opened for one suspicious event. These three are the attack in time order.

Incident 1: “Second-stage fetch from ws-fin-07 after the phishing click”

  • What it is.The infected finance laptop ws-fin-07 (10.20.4.17) connects out to an unknown outside server (203.0.113.47) and pulls down more malware. This is the “second stage” of the attack.
  • Why the system flagged it.Almost all the traffic went one way, and it was far larger than a normal connection. The system scored it 0.996 out of 1 on “how abnormal”.
  • Technique.T1105, called Ingress Tool Transfer in the MITRE ATT&CK catalogue: bringing attack tools in from outside.

You say: “This is the moment the company was breached. Incident 1 is the infected laptop calling out to the attacker to download more malware.”

Incident 2: “Internal discovery sweep from ws-fin-07 against fs-01”

  • What it is.The same laptop starts probing the file server fs-01 (10.20.1.10), trying many ports and services to see what is there.
  • Why the system flagged it.One machine touched many different ports on one server in a short time. Anomaly score 1.000.
  • Technique.T1046, Network Service Discovery: mapping the network to find things to attack.

You say: “Incident 2 is the attacker looking around. Having taken the laptop, they scan the file server to find what is worth stealing.”

Incident 3: “Credential burst against fs-01 from the IT jump host”

  • What it is.A rapid burst of login attempts hits the file server fs-01 from the IT jump host jump-01 (10.20.0.5), trying stolen admin credentials. The jump host is IT’s trusted entry point, so it is marked protected.
  • Why the system flagged it.Very many attempts, arriving with machine-like regular timing. The classifier was certain it was brute force (probability 1.000).
  • Technique.T1110, Brute Force. The report also lists T1110.003 (password spraying) and T1110.004 (credential stuffing).

You say: “Incident 3 is the attacker trying stolen admin passwords on the file server. If one works, they control the server.”

This is the Incident page. It reads top to bottom. Here is each block, in the order it appears, using Incident 1 as the example.

1. Title bar

  • Shows.The incident name, a badge for the type (incident), the status (awaiting approval) and the scenario tag (phishing-lateral).

2. Human Approval Gate (the box you act on)

  • Reason.“Isolate_host on 10.20.4.17 requires approval (trust tier recommend): Policy chose escalate (confidence 0.31) for a critical alert triaged escalate and mapped to T1105.”
